# Video-ORA 42.48 复现包审计（2026-10-20）

## 结论

这个包给出的路线是：冻结 `OraRL/Video-ORA-9B`，只用小规模公开构图数据训练两个几何 LoRA；高光时间定位完全关闭 LoRA，依赖原生 Video-ORA 的零样本事件定位；最后用 PTS、逐帧展开、最大合法裁剪、双向平滑和主体覆盖约束输出提交格式。42.48 的主要来源应是 9B 视频语言模型的时间/主体先验与严格的空间后处理组合，而不是 temporal SFT、RL 或大规模数据训练。

包本身没有比赛测试视频、索引、标签、预测文件或官方 evaluator。42.48 只记录为用户反馈的平台分数，包内明确写着未独立核验。因此可以可靠复现“代码合同和已发布 LoRA 权重”，不能仅凭此包证明另一台机器一定得到 42.48。

## 参数和主干

- 主干是 `OraRL/Video-ORA-9B`，固定 revision：`fc14c214ed1161ad05a7911740b0f6be89d1b6b9`。
- 原始 8 分片经过物理压缩：保持完整输入词表 248,320、32 层和 MLP 12,288，只把未绑定的输出头从 248,320 行裁为 147,456 行；生成时把压缩 logits scatter 回原 token ID。
- 输出头减少 `413,138,944` 个参数，BF16 约少 `0.826 GB`。这是为了把系统压到当前 9B 上限附近，不是量化。
- 包的审计数：主干参数 `8,996,674,800`，注册 buffer `147,538`；两份 LoRA 一起计入后总数 `8,999,771,458`，距 9B 只剩 `228,542` 个参数。每行输出写 `model_params_b=8.999771458`。
- 两个 adapter 不相加：推理时按几何路线二选一，时间定位和主体检测都在 `disable_adapter()` 下运行。

## 两个 LoRA 怎么训练

### A：横屏源 → 9:16 竖裁剪（portrait）

- 训练数据：LIVE-YT-VideoCropping，37 个公开视频，每个取原始帧号 `0/30/60/90/120/150`，共 222 张 1920×1080 图；全部目标是 9:16，监督回答的 `y=500`，只学习横向中心 `x`。
- 适配器：32 层全部覆盖。24 个 linear-attention 层的 `in_proj_qkv/in_proj_z/out_proj` 用 rank 2；8 个 full-attention 层（3、7、11、15、19、23、27、31）的 q 用 rank 3，k/v/o 用 rank 2；共 1,966,080 参数。
- 训练：fresh adapter，240 steps，batch 4，等价 960 个样本使用，`lr=1e-4`、warmup 10、weight decay 0.01、dropout 0.05、余弦调度、梯度裁剪 1.0、seed `20261020`、BF16、非重入 checkpoint 和 CPU activation offload。

### B：竖屏源 → 16:9 横裁剪（vertical）

- 训练数据：GNMC 的 420 张公开人工构图图像，目标 16:9，保留人工中心的 x/y；代码会固定 thumbnail 336、JPEG quality 92、subsampling 0 并逐图校验哈希。
- 适配器：只在 full-attention 层 3、7、11、15、19、23、27、31 的 q/k/v/o 使用 rank 4、alpha 8，共 983,040 参数；A 和主干冻结。
- 训练：210 steps，batch 4，840 个样本使用，等价每张图两次，其他优化设置与 A 相同。README 声明 B 以固定 A 权重初始化，但推理路由只激活 B。
- 包中记录的公开 6 源 DEV 构图 IoU 为 B `0.8413570361`、原生 `0.8224445962`；配对 95% 区间 `[-0.0041493385, 0.0485168219]`，内部 gate 未通过，所以不能把这项小 DEV 对照当成可靠增益证明。

## 推理链路

1. **时间定位：** 每个视频按 30 秒窗口、5 秒重叠切片；每窗 64 帧、模型边长 640。关闭全部 LoRA，greedy 生成“最值得保留的单个事件”，解析 `<answer> start to end </answer>`；解析失败只做一次受限 JSON 重试。跨窗口合并事件。
2. **帧集合：** 用真实解码 PTS，不用平均 FPS 反推时间。事件 `[start,end)` 内输出所有原始解码帧，保持原始 frame ID。
3. **主体锚点：** 建 2 fps、边长 640 的 FrameBank。按事件长度分配 2–12 个锚点；每个锚点由关闭 LoRA 的同一基座输出 `subject_box`。相邻锚点均值像素差大于 0.35 时重置镜头段。
4. **构图候选：** 先生成最大可行目标比例窗口。横屏源且目标 9:16 时启用 A；需要上下裁剪的源且目标 16:9 时启用 B；其他情况保留原生中心窗口。构图提示只要求 `{"crop_center":[x,y]}`，关闭 thinking，greedy，最多 100 token。
5. **后处理：** 在事件和切镜内对锚点插值，双向低通 `tau=0.65`，限制平移速度为 0.15 个画面维度/秒；然后做一个无新增参数的主体保持轨迹投影。投影要求主体与原生窗口的覆盖不下降，并保持合法边界和速度约束。A 只改 x，B 转置坐标后只改 y；没有主体或解析失败则回退原生轨迹。
6. **提交合同：** 导出最大合法窗口的整数 `[x,y,w]`，高度由目标比例推导；每个视频严格按帧升序、无重复、无越界。历史提交统计为 426 视频、134,776 预测帧、3 个空视频；B 改变 133 个视频的 32,305 个纵向位置，新增构图调用 1,632 次，0 次解析回退。

## 为什么这条路线可能接近 43 分

1. **时间任务没有被小数据训练拖坏。** 9B 主干直接承担视频事件理解；这条路线没有用 222/420 张构图图去训练 temporal head，也没有把构图 adapter 污染到时间定位。
2. **监督和官方输出同构。** 训练目标就是最终需要的构图中心，输出始终是最大合法比例窗口，避免了检测框、显著性图到官方 `[x,y,w]` 之间的额外映射误差。
3. **按几何条件拆 adapter。** 9:16 横裁和 16:9 竖裁的自由度不同，A 学 x、B 学 y，减少一个统一 adapter 同时处理两种几何的冲突。
4. **强后处理直接作用于评分量。** PTS 对齐、事件内逐帧展开、最大窗口、平滑和主体覆盖约束都直接影响逐帧空间 IoU；这些步骤不增加参数，却能减少边界、抖动和主体出框。
5. **参数预算被精确卡住。** 输出头物理裁减加上低秩 LoRA，把 9B 模型压到 `8.999771458B`，满足现行参数口径，同时保留大模型语义能力。

## 不能直接照抄的地方

- `42.48` 不是包内独立复现结果。`VALIDATION.json` 明确把它标成“user-reported platform total”，并标明未保证跨机器同分。
- 主干约 18GB、公开训练媒体、比赛测试集、测试索引、PTS、身份向量、历史 predictions 都没有随包提供；只能从有权限的公开来源重建训练数据。
- B 臂没有发现上述 adapter 激活问题：`model_io.py` 在 `add_adapter('other_geometry', ...)` 的分支之后无条件执行 `m.set_adapter('other_geometry')`，所以 `train_arm='b'` 会激活新 adapter。`train.py` 仍应按其 step-1 非零梯度和权重变化断言验收，但不能把 B 的复训风险归因于 active adapter 缺失。
- `VALIDATION.json` 只证明公开样本和合同；没有证明 B 在完整官方测试上的独立贡献，也没有提供官方评测器来拆分 temporal/spatial 得分。

## 对本项目最有价值的可迁移机制

优先迁移“强语义时间基座 + 几何专用空间适配 + PTS/最大窗口/主体约束”这个结构，而不是复制 9B 权重本身。我们现有路线可以先做一个固定时间集合的空间单变量对照：保持当前安全时间集合，只替换官方比例对应的最大窗口、源级构图适配和主体覆盖约束；所有结果仍需真实官方回分确认，公共 crop IoU 不能替代官方分数。

## 证据等级

- **高可信：** 代码执行链、LoRA 张量哈希、参数审计、公开训练清单、PTS/窗口/裁剪/后处理合同；Python 解包后的包校验和 CPU self-test 均通过。
- **中可信：** 原服务器公开样本 GPU 回归、6 源 B DEV IoU 对照；DEV gate 本身未通过。
- **低于独立复现标准：** “平台 42.48”这一单一历史分数；无官方预测文件、无官方 evaluator、无新机器完整 426 路径。
